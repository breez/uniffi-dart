# Map custom types to Dart types through configuration

UniFFI's own bindings let a custom type map to a native type in `uniffi.toml`.
A `u128` sent as a string becomes a `BigInteger` in Kotlin, a `BInt` in Swift
and an `int` in Python. The Dart bindings always made a custom type a `typedef`
of its builtin (#48), so that `u128` reached Dart as a `String`, and every
caller had to parse it.

`[bindings.dart.custom_types.<Name>]` now takes the keys Kotlin and Swift
accept: `type_name`, `imports`, `lift` and `lower`, plus the older
`into_custom` and `from_custom`, which projects that share one `uniffi.toml`
across languages still use. `<Name>` is the custom type's UniFFI name, as in
Kotlin and Swift, so `u128` for `uniffi::custom_type!(u128, String, ...)`.
Nothing is Dart-only.

```toml
[bindings.dart.custom_types.u128]
type_name = "BigInt"
lift = "BigInt.parse({})"
lower = "{}.toString()"
```

A configured type gets a converter class with the usual five methods, which
wraps its builtin's converter and applies `lift` and `lower`. The type itself
becomes a `typedef` of `type_name`, as Kotlin's becomes a `typealias`. Every
position that already went through a converter picks it up: arguments and
returns, async results, records, enums, errors, optionals, sequences, maps,
objects, and callback and foreign-trait methods. `imports` become imports at
the top of each component file that uses the type. Without configuration,
nothing changes.

### Defaults

UniFFI 0.31 allows default values on custom types, as the builtin literal. For
a configured type that literal has to go through `lift`, and Dart parameter
defaults must be constant, which `BigInt.parse('100')` isn't. So a configured
type's parameter is nullable with no default, and the lifted default applies
when it's null: in the constructor's initializer list for records, and in the
lowering for functions, methods and constructors. Unconfigured custom types
keep their literal defaults. (UniFFI's Kotlin bindings render the builtin
literal unchanged, which can't match a remapped type.)

### Relation to #154, #162 and #181

#154 put the builtin's FFI type in callback signatures, so this needs no
signature changes, only a converter on top. #162 is still open: a synchronous
callback returning a custom type over a scalar generates invalid Dart,
configured or not. The fixture leaves that case out.

#181 fixes #162 by recursing into the builtin in `callback_return_handling`.
With this PR, that recursion would call the builtin's converter on the
configured Dart type, for example `FfiConverterString.lower(result)` with a
`BigInt`. Whichever of the two lands second should let custom types take the
final arm instead: the custom type's own converter, written to the slot for its
FFI type. That works for configured and unconfigured types alike. I've run
both together on a fork, with that arm, and #181's `callback-ffi-types` fixture
still passes, as do this fixture's custom-scalar callback returns.

### Testing

The new `custom-type-config` fixture maps three custom types:

- a `u128` over `String` to `BigInt`, with the older key names;
- a `Url` over `String` to `Uri`;
- a `Money` over `i64` to a Dart class from an imported file, without
  `type_name`.

An unconfigured `Count` sits alongside them. The fixture covers every position
above, values outside the `u64` range, and defaults on record fields, function
and method arguments, and a constructor. Unit tests cover the key aliases and
the `{}` substitution.

Without configuration the output is unchanged: bindings generated by `main`
and by this branch are byte-identical for all 26 other fixture libraries,
including `custom_types`. `cargo test --workspace` passes on macOS arm64 with
Dart 3.14.0 (41 test targets), and `cargo clippy --workspace --all-targets -D
warnings` and `cargo fmt --check` are clean.

I also regenerated a real SDK's bindings (the Breez SDK, whose `u128` amounts
are this exact case) through a UniFFI 0.29 port of this branch.
`Payment.amount`, `Payment.fees`, `TokenBalance.balance` and
`PrepareSendPaymentRequest.amount` all come out as `BigInt`. `dart analyze`
reports no errors, and the same 111 non-error findings as without the mapping.
UniFFI 0.29 itself rejects defaults on custom types, so the port's fixture
leaves those out.
